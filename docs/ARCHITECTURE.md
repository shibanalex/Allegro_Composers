# Архитектура Allegro

Allegro — сообщество композиторов, теоретиков, исполнителей и слушателей. Технически это
**модульный монолит**: одно приложение, которое разворачивается целиком, но внутри состоит из модулей
с жёсткими границами. Границы проверяются автоматически (`backend/tests/test_architecture.py`).

## 1. Общая картина

```
Браузер
   │  HTTPS
   ▼
Render (один контейнер, Dockerfile)
 ├─ Nuxt 3 (SSR, порт $PORT) ── страницы; /api/** проксирует внутрь контейнера
 └─ FastAPI allegro.main (127.0.0.1:8000) ── модульный монолит
        │                       │
        ▼                       ▼
   PostgreSQL (Neon)     S3-хранилище (Yandex Object Storage)
   данные                файлы: партитуры, записи, картинки —
                         браузер берёт их прямо из хранилища
```

- **Одна база, одна схема.** Модули не делят таблицы: у каждой таблицы один модуль-владелец
  (см. раздел 3). Внешние ключи между таблицами разных модулей допустимы, это одна база.
- **Файлы не проходят через приложение.** Загрузка — через API (проверка типа и владельца),
  раздача — напрямую из хранилища по публичной ссылке.
- **Наружу открыт только Nuxt.** API слушает только внутри контейнера.

## 2. Устройство бэкенда

```
backend/
├── allegro/
│   ├── main.py            # точка сборки: создаёт приложение и связывает модули
│   ├── models.py          # все таблицы всех модулей — для Alembic и скриптов
│   ├── core/              # общее ядро, модулей не знает
│   │   ├── config.py      #   настройки (.env / переменные окружения)
│   │   ├── db.py          #   движок, сессия, after_commit
│   │   ├── errors.py      #   ошибки прикладного слоя → HTTP
│   │   ├── security.py    #   пароли, JWT, одноразовые ссылки, шифрование почты
│   │   ├── storage.py     #   файлы: локальный диск или S3
│   │   ├── files.py       #   чей это файл: правило владения загрузками
│   │   ├── images.py      #   картинки: проверка, квадратные обложки, лёгкие превью
│   │   ├── ratelimit.py   #   ограничения частоты запросов
│   │   ├── textsearch.py  #   поиск по словам с окончаниями
│   │   ├── slugs.py, schemas.py
│   └── modules/
│       ├── accounts/      # участники, роли, вход, приглашения, администрирование
│       ├── discussion/    # комментарии и рецензии
│       ├── catalog/       # сочинения, синхронизация нот, циклы, библиотека, исполнения
│       ├── publications/  # блог, статьи, новости, материалы
│       ├── media/         # загрузка файлов
│       ├── site/          # страницы «О нас»/«Ссылки», предложения
│       ├── feed/          # лента главной: новое из всех залов
│       ├── notifications/ # уведомления: колокольчик, push, письма-сводки; воркер outbox
│       └── search/        # поиск по всему сайту
├── migrations/            # Alembic
├── scripts/               # демо-данные, «тень», пароль, импорт из Telegram
└── tests/
```

### Слои внутри модуля

| Файл            | Что делает                                                        | Чего не делает                  |
|-----------------|-------------------------------------------------------------------|---------------------------------|
| `api.py`        | HTTP: разобрать запрос, вызвать сценарий, собрать ответ           | бизнес-правил                    |
| `service.py`    | сценарии (use cases): правила, права, одна транзакция на сценарий | не знает про HTTP (кроме ошибок из core) |
| `repository.py` | запросы к базе                                                    | не делает `commit`               |
| `models.py`     | таблицы модуля                                                    |                                 |
| `schemas.py`    | формы данных на входе и выходе (Pydantic)                         |                                 |
| `deps.py`, `roles.py` | только в accounts: кто делает запрос, что ему можно          |                                 |

Мелкие модули (media, search, site) обходятся без `repository.py` — запросов там мало.

## 3. Модули и их границы

| Модуль         | Таблицы                                             | Публичное API для других модулей |

| `publications` | `posts`, `post_links`, `materials`                  | `posts_out`, `recent_posts`, `resolve_post_target`, `search_posts`, `count_posts`, `count_articles` |
| `media`        | —                                                   | —                                |
| `site`         | `site_pages`, `feedback`                            | —                                |
| `feed`         | —                                                   | —                                |
| `notifications`| `notifications`, `notification_settings`, `push_subscriptions` | —                     |
| `search`       | —                                                   | —                                |

**Правила** (их проверяет `tests/test_architecture.py`):

1. `allegro.core` не импортирует модули.
2. Модуль обращается к другому только через его `service`, `schemas`, `deps`, `roles` —
   никогда через `models`, `repository` или `api`.
3. Зависимости идут в одну сторону, по порядку:
   `accounts → discussion → catalog → publications → media → site → feed → notifications → search`.
   Модуль может зависеть только от модулей левее себя, поэтому циклов нет.
4. Всё, что связывает модули «против течения», — регистрации в `allegro/main.py`:
   - каталог и публикации регистрируют в discussion свои объекты для комментариев
     (discussion не знает, что такое опус или пост: ему говорят, существует ли объект, чей он
     и есть ли у него запись для таймкодов);
   - каталог и публикации регистрируют в accounts счётчики для профиля
     (сочинения, исполнения, записи блога, статьи).

Новый модуль: папка в `allegro/modules/`, имя — в `ORDER` в `test_architecture.py`,
роутер — в `main.py`, таблицы — в `allegro/models.py`, миграция — в `migrations/versions/`.

## 4. Сквозные механизмы

**Транзакции.** Один сценарий — одна транзакция: сервис меняет данные и один раз вызывает
`db.commit()`. Побочные эффекты, которые можно выполнять только после успешного сохранения
(например, удалить заменённый файл из хранилища), регистрируются через
`after_commit(db, fn)` из `core/db.py`: выполняются сразу после коммита и отбрасываются при откате.
Так неудачное сохранение никогда не теряет файл, на который ещё ссылается база.

**Ошибки.** Сервисы бросают `NotFound`, `Forbidden`, `Invalid`, `Conflict`, `TooManyAttempts`…
из `core/errors.py`. Ответ всегда `{"detail": "текст для человека", "code": "машинный код"}`.

**Роли и права (RBAC)** (`accounts/roles.py`). Каждое действие, которое что-то меняет, — *право*
(`Capability`). Права участника складываются из трёх слоёв:

1. **что может любой участник**: комментировать, отмечать «нравится», вести блог, делиться материалами;
2. **что добавляет музыкальная роль** — её участник выбирает сам (при регистрации или в «Оформить зал»);
3. **что добавляет служебный уровень** — его назначает администратор:
   модератор (`users.is_moderator`) удаляет чужие комментарии и записи; администратор (`users.is_admin`)
   вдобавок приглашает, публикует новости, правит страницы сайта, отвечает на предложения, назначает права.

| Роль        | Добавляет                    | Вкладки зала по умолчанию |
|-------------|------------------------------|---------------------------|
| composer    | сочинения, статьи            | Выставка · Библиотека · Статьи · Блог · Материалы · О себе |
| theorist    | статьи и обзоры              | Статьи · Блог · Материалы · О себе |
| performer   | исполнения                   | Исполнения · Блог · Материалы · О себе |
| listener    | —                            | Блог · Материалы · О себе |

Таблица живёт в коде, а не в базе: она меняется вместе с возможностями сайта, проверяется тестами и
ничего не стоит при работе. Полная таблица — `GET /api/roles` (вкладка «Права» на странице управления).
В API права проверяются зависимостью `require(Capability.X)` или `can(user, Capability.X)` в сервисах,
на сайте — `useAuth().can('x')`. Исполнение сочинения публикует исполнитель: название берётся из опуса,
так что автор сочинения и автор исполнения никогда не путаются.

**Взаимодействие.**
- «Нравится» (`reactions`, модуль discussion): одна отметка на участника и вещь (сочинение, исполнение,
  запись). Первичный ключ начинается с цели, поэтому счётчики страницы ленты — один сгруппированный
  запрос на тип, а не запрос на каждую запись. Отметки «в тени» не считаются, при удалении вещи удаляются.
- Под записью ленты видны два последних комментария (кеш: Redis или память, `core/cache.py`);
  всё обсуждение открывается прямо под записью и загружается только по нажатию.
- Запись ленты — один объект: подсвечивается при наведении, открывается щелчком по любому месту, кроме
  ссылок и кнопок; длинный текст свёрнут («Развернуть»); у своих записей — меню «Изменить / Удалить».
- Редактирование отправляет только изменённые поля (формы сочинения и записи сравнивают с исходным),
  поэтому нетронутое поле — файл партитуры, привязанное сочинение — не может потеряться.
- PDF-партитуру читатель листает сам; курсор по нотам MusicXML по-прежнему следует за записью.
- Записи ссылаются друг на друга двумя способами: **цитата** (`posts.quote_post_id` — репост со своими
  словами; «Поделиться» сочинением — запись с `opus_id`) и **ссылки в тексте** (…/posts/<slug>,
  …/opus/<slug>). Ссылки разбираются один раз при сохранении и хранятся в `post_links`, поэтому
  страница записи или сочинения показывает «упоминания» (`GET /api/mentions/{post|opus}/{slug}`),
  не читая ничьих текстов.

**Сочинение: жанр и состав.** Вместо «состава», «формы», «сложности» и тегов — один выбор жанра
(`opuses.genre`: соло, соната для инструмента и фортепиано, трио, квартет, квинтет, концерт, симфония…)
и список инструментов (`opuses.instruments`). Жанр подставляет обычный для него состав, композитор его
правит (квартет для четырёх флейт — тоже квартет). Названия инструментов приводятся к одному виду
(«фортепьяно», «ф-но» → «фортепиано»), поэтому каталог фильтрует по инструменту, а поиск его находит.

**Уведомления** (модуль `notifications`, очередь — `core/events.py`). Участники узнают о новых
публикациях всех (сочинения, эскизы, статьи, исполнения, блоги, новости); о своих — нет.

- **Брокер — outbox в базе.** Модуль, который публикует, вызывает `emit(db, "published", …)` в той же
  транзакции, что и сама публикация: событие сохраняется вместе с постом или не сохраняется вовсе.
  Удаление пишет `removed`. Модули-источники не знают про уведомления — зависимость по-прежнему идёт
  в одну сторону. Внешний брокер (RabbitMQ, отдельный воркер) на бесплатном Render потребовал бы
  платного сервиса; таблицу можно заменить Redis Streams или RabbitMQ за тем же `emit`, когда
  одной базы станет мало.
- **Воркер** (`notifications/worker.py`) — фоновая задача в процессе API (запускается в `lifespan`):
  раз в 3 секунды берёт необработанные события по порядку; упавшее событие повторяется до 5 раз,
  затем откладывается с текстом ошибки. Пока бесплатный Render спит, события ждут в базе.
- **Раздача** — одним `INSERT … SELECT` всем участникам, кроме автора и тех, кто «в тени»; повтор
  того же события дублей не создаёт. Выбор «о чём сообщать» (виды публикаций) применяется при
  чтении колокольчика и при отправке push, поэтому, включив вид обратно, участник видит и прошлое.
- **Каналы:** колокольчик в шапке (счётчик раз в минуту и при возвращении на вкладку, страница
  `/notifications` с историей и настройками); push в браузер (Web Push, ключи VAPID выводятся из
  `SECRET_KEY`, подписки — только на адреса push-сервисов браузеров, это защита от SSRF; мёртвая
  подписка удаляется при ответе 404/410); письма — **сводкой** раз в день или в неделю, в 9 утра
  по Москве, не письмом на каждый пост; по умолчанию письма выключены (почта дана для восстановления
  доступа, а не для рассылок). Письма требуют `SMTP_*` (см. DEPLOYMENT.md).

**Эскизы** — быстрые наброски композиторов (право `publish_sketch`): короткое название, одна запись
(голосом прямо в браузере — MediaRecorder, webm/opus или mp4 в Safari — или небольшим файлом), строка
текста и флаг «ищу отзыв» (`posts.seeking_feedback`). Это вид записи (`posts.kind = 'sketch'`), а не
отдельная сущность: лента, лайки, комментарии с кешем, цитаты и поиск работают без нового кода.
Показываются в ленте: фильтры «Эскизы» и «Ждут отзыва»; создаются там же кнопкой «+ Эскиз».
Флаг автор снимает сам («Отзывов достаточно»); механизм отзывов может смениться позже.

**Убранство зала** (`users.hall`, JSON, `HallSettings`): баннер за шапкой, эпиграф, металл отделки
(золото стиля, серебро, медь, кармин, изумруд, сапфир), какие разделы показывать и в каком порядке,
закреплённая запись блога. Одно поле, читается вместе с профилем — без лишних запросов.

**Вход в сообщество** (`REGISTRATION_MODE`): `invite` (по умолчанию) — только по ссылке-приглашению
от администратора; `open` — все; `closed` — никто. Самый первый аккаунт свежего сайта создаётся на
`/setup` кодом `SETUP_TOKEN`, и эта страница закрывается навсегда, как только в базе появился
хоть один участник.

**Одноразовые ссылки** (`access_links`): приглашения и сброс пароля. В базе хранится только SHA-256
от секрета, сама ссылка показывается администратору один раз. Писем сайт не отправляет. Ссылка
«погашается» одним условным `UPDATE … WHERE used_at IS NULL`, поэтому два одновременных запроса не
создадут по одному приглашению двух участников.

**Сеансы.** В токене есть номер версии `users.session_version`. Смена пароля, сброс пароля и кнопка
«Выйти на всех устройствах» увеличивают его — все старые токены перестают действовать, текущее
устройство получает новый.

**Лента** (`feed`, `GET /api/feed?kind=all|works|performances|articles|blogs&before=…`): новые
сочинения, исполнения, статьи и записи блогов всех участников, по времени. Каждый источник отдаёт
свою страницу по составному индексу, модуль сливает их; следующая страница — по курсору `before`
(времени последнего элемента), а не по смещению, поэтому новые записи не сдвигают страницы.

**Почта** необязательна и хранится зашифрованной (Fernet), плюс HMAC-хеш для поиска и уникальности.
Ключи выводятся из `SECRET_KEY` (или `EMAIL_ENCRYPTION_KEY`). Копия базы сама по себе адресов не раскрывает.

**«Тень»** (`users.is_hidden`): аккаунт и всё, что он опубликовал, исчезают с сайта, но остаются в базе.

**Файлы.** Загрузки ложатся в `<назначение>/<username>/<случайное>_<имя>`, поэтому владелец файла —
второй сегмент ключа. Прикрепить можно только свой файл (`core/files.py`). Тип файла проверяется по
расширению и содержимому, а не по тому, что заявил браузер.

**Картинки** (`core/images.py`). Каждая загруженная картинка декодируется (подделка отклоняется), рядом
кладётся WebP-копия до 800 px: `<ключ>.preview.webp`. Имя выводится из ключа, в базе ничего не
хранится; на сайте её показывает компонент `MediaImg` (для старых файлов без копии — оригинал).
Обложки сочинений (`purpose=cover`) обрезаются по центру до квадрата. Копии для файлов, загруженных
раньше, делает `scripts/make_previews.py` — он запускается в фоне при каждом старте контейнера и
пропускает то, что уже сделано.

**Поиск** (`core/textsearch.py`): слова обрезаются до основы («полифония» ↔ «полифонии»), нужны все
слова, «ё» = «е». Работает одинаково на SQLite и PostgreSQL. Полнотекстовый индекс понадобится, когда
записей станут десятки тысяч.

## 5. Фронтенд (Nuxt 3)

- `pages/` — страницы: главная (лента со всех залов: слева фильтры и разделы сообщества, справа новые сочинения, участники и темы),
  зал `/@username`, опус, пост, `/about` («О нас», «Ссылки», «Новости», «Предложения»),
  `/admin`, `/settings` («Оформить зал»), `/register?invite=…`, `/reset?token=…`, `/setup`, `/search`.
- `components/` — `OpusCatalog` (каталог с фильтрами: на главной — всех, в зале — одного
  композитора), `PerformanceList/Card/Form`, `FeedItem` (запись ленты), `HallChannel` (блог зала), `PageTabs`
  (вкладки-разделители папки), просмотрщики нот `ScoreViewer` (PDF) и `MusicXmlViewer`.
- `composables/useAuth.ts` — кто вошёл, настройки сообщества, `can(capability)`.
- **Стили** (барокко и классицизм, романтизм, модерн, авангард): все цвета Tailwind, все шрифты
  (`serif`, `display`, `elegant`, `caps`, `script`) и фон — CSS-переменные (`assets/css/styles.css`,
  `:root` — романтизм). Атрибут `data-hall-theme` на `<html>` переопределяет их, поэтому меняется вся
  страница, включая шапку и подвал. **Стиль сайта** посетитель выбирает значком в шапке
  (`useSiteTheme`, cookie — сервер сразу рисует страницу в нём); пока не выбрал — стиль своего зала,
  у гостя — романтизм. **Зал** всегда показывается в стиле владельца и с его металлом отделки
  (`data-hall-accent`). Шрифты эпохи (`THEME_FONTS`) подгружаются только для показанного стиля.
  Логотип (`.brand`) от стиля не зависит.
- Даты всегда по московскому времени — чтобы сервер (UTC) и браузер рисовали одно и то же.
- SEO: `server/routes/robots.txt.ts`, `server/routes/sitemap.xml.ts`, канонические ссылки
  (`plugins/seo.ts`), разметка schema.org для композиторов и сочинений, переадресация на основной
  домен (`NUXT_PUBLIC_SITE_URL`).

## 6. Миграции

Alembic, `backend/migrations/versions/`. На Render миграции применяются при каждом старте
(`start.sh`). Важная деталь SQLite: изменение колонки пересоздаёт таблицу, и при включённых внешних
ключах это каскадно удаляло бы связанные записи. Поэтому `migrations/env.py` выключает проверку
внешних ключей на время миграции и проверяет их целостность после. Регрессионный тест —
`tests/test_migrations.py` (гоняется и на PostgreSQL: `MIGRATION_TEST_URL=postgresql://…`).

## 7. Решения и почему

- **Модульный монолит, а не микросервисы.** Один разработчик и бесплатный хостинг: отдельные
  сервисы давали бы сетевые вызовы, распределённые транзакции и несколько контейнеров без
  выигрыша. Границы модулей при этом настоящие — любой модуль можно вынести в сервис, заменив
  вызовы его `service` на HTTP/очередь.
- **Без Redis, очередей и WebSocket пока.** См. [SCALING.md](SCALING.md): что и при каких
  признаках добавлять.
- **Ограничения частоты — в памяти процесса.** Хватает, пока экземпляр приложения один; при
  нескольких — вынести в Redis, интерфейс `core/ratelimit.py` не меняется.
