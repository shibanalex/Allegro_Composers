# Производительность и масштабирование

Что ускорит сайт сейчас, и когда понадобятся Redis, очереди, WebSocket и прочая инфраструктура.
Короткий ответ: **сейчас узкое место не в коде, а в размещении**. Инструменты из этого списка
решают задачи, которых у сайта пока нет; каждый добавляет сервис, который нужно держать и оплачивать.

## Что тормозит сейчас и что поможет

| Проблема | Цифры (сентябрь 2026) | Что делать |
|---|---|---|
| Сайт на Render в США (Орегон), база Neon во Франкфурте | каждый запрос к базе +150–400 мс, главная ~2 с | **Пересоздать сервис Render в регионе Frankfurt** (`region: frankfurt` в render.yaml). Страницы станут в 3–4 раза быстрее. Лучше вместе с покупкой домена — адрес всё равно сменится |
| Бесплатный Render засыпает через 15 минут | первое открытие ~1 мин | «Будильник» (cron-job.org) на `/robots.txt` раз в 10 минут, или платный тариф Starter |
| Бесплатный Neon засыпает через 5 минут | первый запрос +0,5–1 с | Терпимо. Не будить базу «будильником» — израсходует бесплатные часы |
| 0,1 CPU на бесплатном тарифе | серверная отрисовка страниц | Платный тариф при росте посещаемости |

## Инструменты: нужны ли и когда

### PgBouncer — уже используется
Neon даёт пул соединений PgBouncer (адрес с `-pooler`). Приложение под него настроено: отключены
серверные prepared statements (`core/db.py`). Ничего добавлять не нужно.

### Redis — не сейчас
Нужен, когда:
- **экземпляров приложения станет больше одного** — ограничения частоты запросов
  (`core/ratelimit.py`) должны стать общими; интерфейс уже отделён, меняется только хранилище;
- **захочется кешировать тяжёлые выборки** (главная, счётчики) — но сначала нужно перенести
  сервис во Франкфурт: после этого кеш почти ничего не даст;
- понадобится очередь фоновых задач (см. ниже) — Redis подойдёт и для неё.

Бесплатные варианты без карты есть (Render Key Value, Upstash), но добавлять стоит по признаку, а не заранее.

### RabbitMQ + Celery — нет; очередь — когда появятся долгие задачи
Фоновые задачи нужны, когда появится работа длиннее пары секунд или письма:
перекодирование wav → mp3, волновая форма записи, рассылка уведомлений, рендер MIDI из MusicXML.
Для масштаба Allegro RabbitMQ + Celery — это два сервиса и тяжёлая настройка. Легче:
**arq/RQ на Redis** или очередь в самой PostgreSQL (например, procrastinate) — отдельный процесс-воркер
и никакого нового хранилища. Лёгкие вещи уже сейчас делаются после коммита (`after_commit`).

### Centrifugo (WebSocket) — когда появится «живое»
Нужен для обновлений без перезагрузки: новые комментарии в открытой ветке, уведомления, чат.
Сейчас таких функций нет. Первый шаг, когда появятся, — Server-Sent Events прямо из FastAPI
(ничего нового разворачивать не нужно); Centrifugo — при тысячах одновременных подключений.

### Traefik / Nginx — не нужны на Render
Render сам принимает HTTPS, отдаёт сайт через свою пограничную сеть (в заголовках ответа видно
Cloudflare) и направляет запросы в контейнер. Внутри контейнера Nuxt проксирует `/api` в FastAPI,
файлы отдаёт Yandex Object Storage. Прежний шлюз nginx удалён вместе с разбиением на сервисы.
Traefik или Caddy (либо nginx) понадобятся, если переехать на собственный VPS с несколькими
контейнерами: TLS, маршрутизация, ограничения частоты на входе.

## Порядок, если сайт начнёт расти

1. Регион Frankfurt + свой домен (быстрее, стабильный адрес).
2. Платный тариф Render (не засыпает, больше CPU) — первое, что реально ускорит под нагрузкой.
3. Кеш заголовков для статических страниц и файлов (`Cache-Control`), CDN для домена.
4. Redis: общие ограничения частоты и кеш — когда экземпляров станет несколько.
5. Очередь фоновых задач — когда появятся перекодирование, письма, уведомления.
6. SSE/Centrifugo — когда появятся «живые» функции.
